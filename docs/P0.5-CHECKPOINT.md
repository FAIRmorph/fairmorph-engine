**Rahmenwerk:** v0.12 Kapitel **08**, **11** (ökologische Profile v0.8), **12** (lokale Registry und Preflight), **13–15** (Feldsemantik, Mapping und Forschungsdatennachweise).

## Architekturentscheidung

1. **Profilfreier technischer Import:** Unbekannte oder unstrukturierte Quellen bleiben weiterhin valide `imported_unmapped`; weder Import noch ein rein technischer DAG müssen eine ökologische Interpretation erzwingen.
2. **Verpflichtende Profile für semantische RUNs:** Jede Pipeline mit `entities` benötigt jetzt ein vollständiges `profile_bindings` mit **exakten** `schema_id`, `schema_version` und `schema_sha256` für den gemeinsamen Envelope und jeden projizierten Entitätstyp. Die frühere unprofilierte P0.2-Variante wird **nicht** weiter unterstützt. Es sind keine Altläufe zu migrieren.
3. **Kern-Envelope versus Domänenattribute:** Ein Metadata-Envelope enthält `entity_id`, `entity_type`, `schema_version`, `metadata_revision_id`, `recorded_at`, `source`, `review_status`, `attributes` und `field_provenance`. Nur `attributes` werden anhand des gewählten Domänenprofils geprüft; technische Identitäten und fremde Entitätsreferenzen bleiben getrennt.
4. **Nicht jede Datenzeile ist eine Metadatenrevision:** Das RUN/2-Ergebnis bleibt Parquet. SQLite nimmt ausschließlich *explizit kuratierte und vom verantwortlichen Nutzer bestätigte* Metadatenrevisionen auf; kein automatischer Zell- oder Zeilenspiegel. Die sparsame P0.3-Änderungsaudit-Entscheidung bleibt bestehen.
5. **Unveränderliche Historie:** Neue Metadatenrevisionen werden append-only gespeichert und referenzieren ihre Elternrevision; `current_metadata_revisions` ist ein transaktional aktualisierter Zeiger. Ein RUN friert die aktive, freigegebene Auswahl mit Sequenzgrenze und Hash in `inputs.snapshot.json` ein und ist später erneut verifizierbar.

## Gelieferte v0.12-Verträge

Die mitgelieferte Datei `contracts/profile-bundle.v012.json` enthält die acht ökologischen **v0.8 JSON Schema Draft 2020-12**-Profile:

| Profil | Mindestanforderung im JSON-Schema | PoC-Grenze |
| --- | --- | --- |
| `SamplingEvent` | `event_type` | Allgemeines Event, kein GPS-, Taxon- oder Transect-Zwang; `event_time` auf Reihenfolge prüfbar |
| `Occurrence` | Keine Pflichtfachfelder | Keine erfundene Artbestimmung/Occurrence |
| `MeasurementOrFact` | `measurement_type`, `value` | `0` gültig; negativ angegebene Unsicherheit unzulässig; Nullwert-Missing-Grund aus P0.2 |
| `Sample` | Keine Pflichtfachfelder | Typ/Probenkette nicht vollständig geprüft |
| `MediaAsset` | `file_object_hash`, `media_type`, `original_filename` | SHA-Format geprüft, Objektstore-Bezug/GPS-Logik später |
| `SpatialFeature` | Geometrie, Geometrietyp, CRS, Quellenangabe | Keine vollständige Topologie/CRS-Validierung |
| `Transect` | Keine Pflichtfachfelder | Nur Schemaentwurf, keine ausführbare neue Projektion |
| `Dive` | Keine Pflichtfachfelder | Nur Schemaentwurf, keine ausführbare neue Projektion |

Das neunte Schema ist der technische `metadata-envelope`; der Feldherkunftseintrag ist als lokales Unter-Schema eingebettet (entsprechend dem zehnten v0.12-Vertrag `provenance-entry`). Dies vermeidet jede ungeprüfte externe `$ref`-Auflösung. **Wichtige Abweichung:** Das Original in v0.12 enthält stattdessen einen separaten relativen `$ref`. Die lokal eingebettete Variante ist **nicht byteidentisch**; ihre SHA-256-Pins dürfen nicht als Hashes des unveränderten v0.12-Originalschemas ausgegeben werden. Ein bewusstes Schema-Normalisierungsreview bleibt offen. Alle Schemas bestehen `Draft202012Validator.check_schema`. Die ausgeführte Entitätsvalidierung umfasst die bereits in P0.2 realisierten Typen `SamplingEvent`, `Occurrence`, `MeasurementOrFact`; die anderen Profile werden installierbar und einzeln validierbar mitgeliefert.

Die bestehende Projekt-Registry wurde um `kind="domain"` erweitert; Profile werden explizit als `approved` mit bestätigendem Benutzer installiert. Neue Schema-IDs und -Versionen können danach registriert werden, **ohne** den SQLite-Kernvertrag zu migrieren. Ein einmal registrierter Hash/Version-Eintrag ist unveränderlich. Die PoC-Pipeline wählt nur die lokal gebündelte Schema-Identität; neue Domänenprofile/Komposition erfordern spätere Erweiterung.

## Beispiel-Workflow

1. Unveränderte Quelldaten importieren und SourceFieldDefinitions bestätigen (P0.2).
2. `fairmorph-engine install-profile-contracts --project ./survey.fairmorph --confirmed-by researcher`.
3. Profilbindungstemplate anzeigen: `fairmorph-engine profile-bindings --project ./survey.fairmorph --entities SamplingEvent,MeasurementOrFact`.
4. Die zurückgegebenen Pins unter `profile_bindings` in die deklarative Pipeline kopieren. Pipeline registrieren, Projektion ausdrücklich bestätigen, Pipeline auswählen.
5. Bei Bedarf einzelne fachliche Metadaten unter bestätigter Entitäts-ID als JSON-Revision registrieren:
   ```sh
   fairmorph-engine record-metadata --project ./survey.fairmorph \
     --pipeline-sha256 <sha> --entity-type SamplingEvent --entity-id e1 \
     --attributes attributes.json --provenance provenance.json \
     --source user_confirmed --confirmed-by researcher
   ```
   Beispiel `attributes.json`: `{"event_type":"point_count","remarks":"Feldbuch geprüft"}`. Beispiel `provenance.json`: `{"/attributes/event_type":{"source_type":"user_confirmed","source_ref":"fieldbook-42"},"/attributes/remarks":{"source_type":"user_confirmed","source_ref":"fieldbook-42"}}`.
6. Projekt-RUN erzeugen und `verify-project` ausführen. Der RUN bindet Konfiguration, Feldbestätigungen, Relations-Snapshot (P0.4), Schema-Pins und optional bestätigte Metadatenrevisionen.

Eine geänderte Metadatenrevision verlangt `--parent-revision-id <current-id>`; sie überschreibt weder die alte Revision noch den früheren RUN. `show-metadata-snapshot` zeigt die aktuelle Auswahl.

## Nachweis-/Abnahmekriterien

- Alle v0.12-Profilschemas sind lokal maschinenlesbar und gültig; keine unkontrollierte Online-`$ref`.
- Semantic RUN ohne Profilpins oder ohne ausdrücklich bestätigte lokale Schema-Version wird abgelehnt. Technischer Import ohne Mapping bleibt möglich.
- RUN-Ergebnistabellen werden gegen das festgelegte Entitätsprofil geprüft: unbekannte Attribute, fehlende Pflichtwerte, negative Unsicherheit sowie ungültige Profile werden erkannt. `0` bleibt `0`; `null` wird nicht zu einer Nullzählung umgedeutet.
- Metadata-Envelope muss den Entitätstyp und eine existierende technische `entity_id` treffen. Feld-Provenienz-Pointer müssen genau die angegebenen Attribute adressieren. Nutzerfreigabe und Quellenart sind getrennt.
- Schema-Version, Envelope-Revision und Relationszustand werden im RUN eingefroren. Neue Profilversionen bzw. neue kuratierte Metadata-Revisionen verändern die Verifizierbarkeit bereits entstandener RUNs nicht.
- P0.1–P0.4-Regressionstests werden auf den **neuen** Pflichtvertrag umgestellt (keine Altformat-Kompatibilität). Linux/Windows Ruff + pytest müssen grün sein.
