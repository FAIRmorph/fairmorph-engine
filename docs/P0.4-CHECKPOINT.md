# P0.4 – versionierte fachliche Relationsassertions (v0.12 vertikaler PoC)

**Branch:** `refactor/framework-v012-foundation` · **PR:** [#10](https://github.com/FAIRmorph/fairmorph-engine/pull/10)  
**Grundlagen:** v0.12 Kapitel 09–11, ADR-033–035 und ADR-039. **Status:** technischer PoC; keine allgemeine Produktionsmigration.

## Architekturentscheidung

Eine Beziehung ist eine **eigenständige fachliche Aussage**, nicht die Position eines Datensatzes im Dateisystem und nicht eine veränderliche Liste im Entitätsobjekt. Die Entität behält ihre technische `entity_id`. Jede freigegebene Zuordnung steht als selbstständige, versionierte `assert`-, `replace`- oder `retract`-Assertion im projektlokalen SQLite-Katalog. Alle Aktionen sind vom **verantwortlichen Nutzer** ausdrücklich bestätigt; ein zweiter unabhängiger Reviewer ist nicht vorgeschrieben.

Der PoC bindet jede Assertion an einen konkreten, bestätigten `fairmorph.pipeline/1`-SHA, an eine versionierte Relation-Profildefinition mit SHA-256 und an bereits projizierte technische Entitäts-IDs. Provenienz (`source.kind` und `source.reference`), Bestätigung (`review.status` und `review.confirmed_by`), Aufzeichnungszeit (`recorded_at`) und optionale fachliche Gültigkeit (`valid_from` / `valid_to`) sind getrennte Felder.

## Minimaler ausführbarer Prädikatvertrag

`src/fairmorph_engine/contracts/relation-profile.poc.json` ist das versionierte Profil `fairmorph.ecology.core/0.12-poc.1`. Sein SHA-256 wird für Assertions und RUN-Snapshots mitgeführt.

| Prädikat | Subjekt → Objekt | Integritätsbedingung |
| --- | --- | --- |
| `parent_event` | SamplingEvent → SamplingEvent | höchstens ein unmittelbarer Parent pro Event, **zyklenfrei** |
| `event_occurrence` | SamplingEvent → Occurrence | höchstens ein Event pro Occurrence im PoC-Profil; ein Event kann mehrere Occurrences haben |
| `event_measurement` | SamplingEvent → MeasurementOrFact | höchstens ein direktes Event pro Messung im PoC-Profil |
| `occurrence_measurement` | Occurrence → MeasurementOrFact | höchstens eine direkt zugeordnete Occurrence pro Messung im PoC-Profil |

Weitere Prädikate des v0.12-Vokabulars (z. B. Event–Sample, Event–Media, Event–Transect, Media–FileObject und SpatialFeature-Assertions) sind **nicht implementiert**. Insbesondere wird weder ein Transect noch GPS noch eine Occurrence als Voraussetzung für `SamplingEvent` gefordert. Die genannten Kardinalitäten gelten **nur für dieses explizite PoC-Profil**, nicht als universelle DwC-Annahme.

Wenn ein bestätigtes P0.2-Feld bereits eine technische Event-/Occurrence-Referenz enthält, darf eine separate Relation-Assertion dem nicht widersprechen. Ziel-IDs und Typen werden aus den tatsächlich erzeugten Entity-Projektionen geprüft. Vorherige Assertions werden **nicht** automatisch durch eine neuere bevorzugt: Konflikte führen zu einem Fehler und erfordern bewusste Korrektur.

## Speicherung, Historie und RUN

- **SQLite `relation_assertions`:** monotone `sequence`, `relation_id`, `assertion_id`, Operation, `supersedes_assertion_id`, Pipeline-SHA, kanonisch prüfbares JSON und Payload-SHA-256. UPDATE/DELETE werden durch Append-only-Trigger abgelehnt.
- **SQLite `current_relations`:** transaktional gepflegte Referenz auf die aktive Assertion je `relation_id`. Nach `retract` verschwindet sie aus der aktuellen Sicht, bleibt aber als historische Assertion vorhanden. `replace` schreibt ein neues Ereignis und versetzt lediglich den Current-Pointer.
- **RUN/2 `inputs.snapshot.json`:** enthält für bestätigte Entity-Pipelines zusätzlich `relations_snapshot` mit Profil-/Schema-ID, Profil-SHA, Konfigurations-SHA, `through_sequence`, sortierten aktiven Assertions inklusive Hash und `snapshot_sha256`.
- **Historische Reproduzierbarkeit:** `verify-project` liest Assertions bis zur **im RUN eingefrorenen Sequenz** und rekonstruiert den damaligen Zustand, auch wenn danach `replace` oder `retract` hinzugefügt wurde. Eine manipulierte Assertion, ein beschädigter Profil-Hash oder ein inkonsistenter Snapshot wird abgewiesen.
- Keine Duplikation aller Quellzeilen in SQLite. Die P0.3-Entscheidung für ein **sparsames Änderungs-Audit** gilt unverändert.

## Demonstrationsablauf (CLI)

Voraussetzung: `register-pipeline`, `confirm-projection` und `select-pipeline` wurden für die Entity-Pipeline ausgeführt; `e1` und `e2` sind bereits vorhandene technische Event-IDs.

```sh
fairmorph-engine assert-relation --project ./survey.fairmorph \
  --pipeline-sha256 <sha> --predicate parent_event \
  --subject-id e2 --object-id e1 \
  --confirmed-by researcher --source-reference field-note-42

fairmorph-engine show-relations --project ./survey.fairmorph --pipeline-sha256 <sha>

fairmorph-engine run-pipeline --project ./survey.fairmorph

fairmorph-engine replace-relation --project ./survey.fairmorph \
  --pipeline-sha256 <sha> --relation-id <returned-relation-id> \
  --object-id e3 --confirmed-by researcher --source-reference correction-note-1

fairmorph-engine retract-relation --project ./survey.fairmorph \
  --pipeline-sha256 <sha> --relation-id <returned-relation-id> \
  --confirmed-by researcher --source-reference correction-note-2

fairmorph-engine verify-project --project ./survey.fairmorph
```

Die IDs, Quelle und Aussage werden **nicht** durch die Engine erraten. Der Benutzer kann dieselbe Person sein, die Felddefinition und Projektion bestätigt hat.

## P0.4-Abnahme des vertikalen Schnitts

- Eine bestätigte Relation wird in der aktuellen Sicht sichtbar; der RUN enthält die exakt gepinnten Assertions und das Profil.
- `retract` entfernt die aktive Beziehung, nicht die historische Aussage; alte RUNs bleiben prüfbar.
- `replace` erhält `relation_id`, nutzt eine neue `assertion_id`, referenziert die abgelöste Assertion und wechselt die aktuelle Projektion transaktional.
- Event-Hierarchien mit Zyklen, ungültige Entity-IDs, fremde Typen, Konflikte mit bestätigten Feldmappings sowie ungültige Kardinalitäten werden vor dem Commit blockiert.
- Vorschläge oder aus Daten extrahierte Beziehungen können nicht **automatisch** aktiv werden: Aufruf und Bestätigung durch einen Nutzer sind Pflicht, Herkunftsklasse und Bestätigung bleiben unterscheidbar.
- Das SQLite-Log verweigert UPDATE und DELETE; der Current-Pointer wird vor jeder Mutation gegen das Log abgeglichen.
- Der vorhandene P0.1–P0.3-Pfad und der historische CS-PHOC-Referenzpfad bleiben testbar.
- Ruff und pytest auf Linux **und** Windows müssen erfolgreich sein, bevor der PoC als abgenommen markiert wird.
