# P0.3 checkpoint – source-record and source-cell lineage (v0.12 PoC)

**Status:** Implemented in PR [#10](https://github.com/FAIRmorph/fairmorph-engine/pull/10); green Linux/Windows CI is required for final technical acceptance. **Scope:** a vertical proof of reproducible provenance, not a production-scale lineage service.

**Framework references:** v0.12 chapters **05** (immutable original inputs and RUN artifacts), **13** (original field → semantics → target and source-cell lineage in preview) and **15** (row identity is *technical provenance*, not durable biological identity; hash-pinned lineage/finding outputs with each RUN; Polars source-cell checks). The generic `fairmorph.pipeline/1` is the already existing P0.1/P0.2 vertical processing path.

## Delivered PoC slice

1. The import pins each immutable source resource and original-object SHA-256; original CSV/Parquet bytes remain untouched.
2. The DAG materializes deterministic processing results using the existing allowlisted operators. `table.select/1`, `table.filter/1`, `table.distinct/1`, `table.derive/1`, `table.unpivot/1` and `table.join/1` now have explicit output-row/source-cell tracing. Join order is pinned (`left_right`); duplicate source values are never used to guess row identity.
3. For optional v0.12 `SamplingEvent`, `Occurrence` or `MeasurementOrFact` projections, provenance follows the explicit P0.2 target-field-to-source-column bindings into the semantic output table. This does not infer taxonomic or geographic meaning.
4. Every generic pipeline RUN/2 writes `audit/lineage.parquet`. The RUN manifest records its relative path, size and SHA-256. `verified_run` additionally reconstructs provenance from pinned inputs/DAG and compares it with the published evidence, rejecting both byte tampering and a replaced artifact with a forged internal manifest checksum.
5. The output Parquet tables and the lineage are checked against recomputed DAG results on verification. Neither the evidence nor result tables are duplicated as millions of SQLite records.

## Artifact contract `audit/lineage.parquet`

| Column | Meaning |
| --- | --- |
| `output_table` | Published named DAG table or semantic entity profile |
| `output_row_index` | **Zero-based** row offset in the published Parquet table |
| `output_column` | Output field for a cell lineage entry; null for record lineage |
| `lineage_type` | `record` or `cell` |
| `source_resource_id` | Imported technical resource identity |
| `source_object_sha256` | Exact immutable source-object byte hash |
| `source_row_index` | **Zero-based data-row offset** in the original CSV/Parquet (not physical CSV line number and **not** a scientific identifier) |
| `source_column` | Original physical source field (null for record-only links) |
| `source_kind` | `data_row`, `data_cell`, `column_header` or `derived` |

A record link lists each imported row that contributed to one published output row (including both matched join sides). A cell link lists each original source cell used to form the output field. Several original fields can contribute to a derived value. A literal or an unmatched join value has an explicit `derived` cell entry with null source fields; a generated unpivot variable name is not falsely attributed to a source header. The `when` operator includes the input condition as a causal dependency and only the selected value branch.

A skipped row from `table.filter/1` or `table.distinct/1` is not a published record and therefore has no output lineage entry. `null` and numeric zero remain distinct in the result Parquet. The field-level semantics and user confirmation are separately frozen by P0.2 in the RUN input snapshot.

## Test evidence and acceptance

Regression tests cover a second imported lookup resource and join, filter, derive, conditional values, unpivot, first-wins distinct, unmatched joins, numeric zero, exact source-column and row-index tracing, semantic MeasurementOrFact projection, a manifest hash failure and a falsified hash with semantically invalid lineage. The Linux and Windows CI matrix runs Ruff and pytest; the exact successful run and commit should be recorded when the full matrix completes.

Acceptance is **technical**, not a formal scientific validation of a dataset. In particular, CS-PHOC cardinality/reference numbers remain independent E2E acceptance for the later real-data demonstration.

## Intentional scope boundary / remaining work

| Next package | Deferred capability |
| --- | --- |
| **P0.3 hardening** | Resource-budgeted/streaming lineage rather than eager Python source-cell sets; scalable partitioned Parquet and performance thresholds |
| **P0.4** | Independently versioned, retractable domain-relation assertions and frozen relation snapshots (v0.12 chapter 09) |
| **P0.5** | Full profile and metadata-envelope registry, formal source-type/aggregation/measurement validation, stable key contracts |
| **P0.6** | Workbench preview/explanation of origin → semantics → operation → target, plus explicit user confirmation |
| **P0.7** | Generic EML/DwC-A/GeoPackage publication adapters and profiles |
| **P0.8** | Real CS-PHOC dataset regression, second independent vertical dataset and larger-data/cross-platform acceptance |
| **Production hardening** | Incremental/restart-safe lineage, provenance indexing/query API, cryptographic signatures/access control, multi-GB scale and fully versioned schema/migration policies |

**Architectural decision:** the demonstration freezes exact source cells in immutable RUN artifacts, while SQLite remains a metadata/registry/catalog store. Source data-row offsets are technical evidence only. The PoC does not claim a complete enterprise provenance graph, streaming guarantees, user authentication, publication approval or all v0.12 schema/relationship contracts.
